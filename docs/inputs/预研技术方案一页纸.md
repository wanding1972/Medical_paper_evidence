# Evidence Check｜预研技术方案一页纸

| 模块 | 结论 |
|---|---|
| 决策建议 | **建议进入分阶段 POC，不建议直接产品化。** Phase 1 的引用完整性审计技术风险低；Phase 2 的 Claim–Evidence 语义审计可做，但必须以“需复核”呈现，并通过人工标注集证明可靠性。 |
| 核心前提 | 首版限定为数字引用、可复制文本的 DOCX/Markdown、文本型 PDF、单章节 ≤30 篇文献；扫描件、复杂表格图像、无法提取全文的 PDF 一律 fail-closed，输出“不可审计”。 |
| 推荐技术路线 | **封闭语料证据审计**：只处理用户提交且正文已引用的文献。正文/引用确定性解析 → Claim 候选提取 → 引用文献内混合检索 → 候选 Evidence Span → 结构化比对 → 纯规则引擎输出 Finding。无需联网补文献、RAG 知识库、LLM Wiki 或本体。 |
| LLM 边界 | LLM 仅输出受 JSON Schema 约束的候选 Claim、限定项和候选证据片段；不得直接判定“正确/错误”，不得生成最终 Finding。规则引擎负责严重等级与 fail-closed 策略。 |
| POC 目标 | 验证“用户能否定位并修改具体问题”，而非验证模型是否能评判医学结论。以人工标注的 Claim–Citation–Evidence 样本评估，并保留全文定位、模型版本、提示词版本、规则版本和输入哈希。 |
| 技术可行性 | **高**：数字引用解析、缺引文、错编号、无全文、定位报告。<br>**中**：范围不一致、因果夸大、数值不一致。主要难点是跨语言改写、PDF 版式、一个 Claim 由多篇证据共同支持，以及观察性研究表述的语境判断。 |
| 预估效果 | 在输入边界严格执行时，数字引用解析 ≥98%、`missing_citation`/`unresolved_reference` 精确率 ≥95% 具有可行性。语义型 Warning 的目标精确率 ≥80%，但这是待 POC 验证的门槛，不是现阶段承诺；100 条样本只能得到方向性结论，进入产品化前应扩充独立盲测集。 |
| 成本与周期 | POC 约 6–10 人周：后端/文档处理 1 人、模型与评测 0.5–1 人、前端 0.5 人。基础设施和模型调用成本通常不是主成本；人工标注、医学专家复核、PDF 异常处理与合规审查才是主要投入。 |

## 推荐处理流程

```text
上传与安全门禁
→ DOCX / Markdown / PDF 解析
→ 数字引用解析及 reference 映射
→ Claim 候选抽取与限定项结构化
→ 仅在已引用文献中检索候选证据段
→ Claim–Evidence 受约束比对
→ 纯规则引擎生成“需复核”Finding
→ 可追溯审计报告与定时删除
```

检索首版建议采用 **BM25 + 章节/摘要/结果段落加权 + 可替换语义重排序器**。不需要向量数据库：每项任务最多 30 篇文献，可在任务内建立临时索引。仅 BM25 对中英文改写、医学同义词和低词面重合证据的召回风险较高；语义重排器作为候选召回补充，但其结果不能绕过规则核验。

## 技术选型

- 服务端：Python、FastAPI、Pydantic、SQLAlchemy、PostgreSQL。
- 异步任务：Redis + Celery/Dramatiq；PDF 解析、OCR、检索和 LLM 调用均在 worker 中执行。
- 文档：`python-docx`、PyMuPDF；文本坐标、页码和段落锚点作为一等数据保存。
- 检索：SQLite FTS 或内存 BM25 索引；任务完成后随解析结果删除。
- 模型：可替换 LLM adapter，结构化输出、低温度、保留原始响应；支持关闭外部模型。
- 报告：HTML/Markdown 首发；PDF 导出延后。
- 元数据：DOI/PMID 仅用于书目信息核验与补全，不用于寻找新文献。NCBI 的 E-utilities 可提供 PubMed 等数据库访问；应做缓存、队列和限流处理。([NCBI API 文档](https://www.ncbi.nlm.nih.gov/home/develop/api/))

## 技术路线比较

| 路线 | 结论 | 原因 |
|---|---|---|
| 规则解析 + 封闭文献检索 + 受限 LLM | **推荐** | 可追溯、可限制越界、适合证据审计；每项 Finding 都能回到正文与证据原文。 |
| 纯 LLM 长上下文判读 | 不推荐 | 容易漏掉定位细节、难复现，且会把“未发现证据”误写成“证据错误”。 |
| RAG / LLM Wiki | 不推荐首版 | 本产品禁止联网找文献，且任务对象是用户上传的有限引用集；通用知识库会引入未引用来源并破坏审计边界。 |
| 本体/知识图谱 | 延后 | 首版只需 Population、Disease、Intervention、Outcome、Time 等受限限定项；除非验证出跨文献关系推理是主要误差源，否则收益不足以覆盖建模成本。 |

## POC 设计与退出门槛

| 阶段 | 验证内容 | 通过条件 |
|---|---|---|
| POC-A：引用完整性 | DOCX/Markdown 解析、数字引用区间、编号映射、定位报告 | 数字引用解析 ≥98%；规则型 Finding 精确率 ≥95%；每条问题均可定位。 |
| POC-B：证据对齐 | Claim 抽取、文献内检索、范围/因果/方向/数值审计 | 人工盲评下，范围与因果类 Warning 精确率 ≥80%；每条语义 Finding 必有可查看证据段或标记为不可审计。 |
| POC-C：使用价值 | 5–10 名目标用户完成真实章节审计 | 多数用户能独立定位并修改至少一处问题；至少 3 人愿意为完整报告付费或预约下一章审计。 |

**停止或降级条件：**

- 文本型 PDF 中的证据定位无法达到可复核要求：退回 Phase 1，仅做引用完整性产品。
- 语义型 Warning 精确率低于 80%，或用户频繁认为“误报”：不开放自动审计结论，只保留证据候选检索与人工复核界面。
- 用户主要需求是“找遗漏文献、润色论文或给发表评分”：停止，因为这与产品的审计边界冲突。

## 主要风险与控制

| 风险 | 等级 | 控制措施 |
|---|---|---|
| PDF 解析错误、扫描件、双栏和表格导致证据错位 | 高 | 首版只支持文本型 PDF；保存页码与原文片段；解析置信度不足即 `not_assessable`。 |
| Claim 与证据的语义比对误报 | 高 | 规则与 LLM 分离；LLM 只提候选；全部标为“需复核”；采用医学专家盲评集持续校准。 |
| 文献版权与全文再利用 | 高 | 只处理用户上传文件；不训练、不长期留存、不批量抓取。若后续接入 PMC，必须逐篇处理许可；PMC 并非所有文章都允许文本挖掘或再利用。([PMC 版权说明](https://pmc.ncbi.nlm.nih.gov/about/copyright/)) |
| 上传内容含病例或患者信息 | 高 | 前端警示不足以构成控制；上传前确认、文本 PII 扫描、命中后阻断/人工复核、24 小时自动删除及日志最小化。 |
| 外部 LLM 的数据出境与服务合规 | 高 | 外部调用前取得明确同意；提供本地/关闭模型选项；记录供应商与处理范围。如面向中国境内公众提供生成式 AI 能力，应在上线前完成适用性与合规评估。([国家网信办暂行办法](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)) |
| PubMed/PMC 元数据依赖 | 中 | 缓存 DOI/PMID 映射、限流、失败降级为“元数据未核验”。NCBI E-utilities 未使用 API Key 时的请求频率有限制。([NCBI E-utilities 说明](https://www.ncbi.nlm.nih.gov/books/NBK25497/pdf/Bookshelf_NBK25497.pdf)) |

## 下一步决策

批准 POC-A 与 POC-B，但先完成三项前置工作：

1. 建立 100 条最小标注集，并额外规划独立盲测集；标注“支持、部分支持、矛盾、不可核验”的依据与证据坐标。
2. 明确首发语言组合：中文论文配英文文献、英文配英文，或中文配中文；这会直接决定检索与限定项抽取方案。
3. 制定上传文件、模型处理、删除机制和版权声明的产品文案，并在接入外部模型前进行隐私与合规审查。

最终判断：**技术上走得通，且 Phase 1 有较低风险的独立价值；Phase 2 值得验证，但必须被定位为“可复核的证据提醒系统”，不能包装成医学事实裁判或论文质量评分器。**
